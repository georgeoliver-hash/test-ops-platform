# ETM Coherence & Grounding Audit — Part 2 (suite_ETM.json indices 228–454)

**Scope:** 227 cases (idx 228–454, IDs 4100718–4100950), WinCE ETM driver ticketing machine. Report-only; no edits made.

**Summary:** 220 of 227 cases (idx 228–447) are pure "Screen Validation" template cases — title, preface, precondition, and single WHEN-displayed/THEN-matches-design step all reference the identical screen name, so they are coherent by construction and impossible to make internally contradictory; all audited clean. The only functional cases are the 7 Regression cases (idx 448–454). **Findings: 0 High, 2 Medium, 3 Low.** No incoherent-or-impossible cases found. The dominant issue is a generic "check the CloudFare activity log / the corresponding event is recorded" step bolted onto regression cases where no such audit event corresponds to the action under test (per FBD-100358, the Activity Log records a defined set of event types, not performance/hardware metrics).

Notes not raised as per-case findings (systemic, low value): every title carries a mojibake em-dash ("â€"") uniformly across the whole suite; several design-screen numbers collide across distinct cases (e.g. two "02.0.3.1", two "08.2.1", two "01.1.6", two "02.2.1", "09.5.3"/"10.7.3"). Neither is an internal-coherence defect in the test itself.

## Findings

**C4100950** | Medium | salvageable-grounding / conflation | Title/preface/S1/E1 test *ticket print speed* for a 110 mm ticket (defect 301258) — a local hardware performance metric — yet S2/E2 append "WHEN the CloudFare activity log is checked / THEN the corresponding event is recorded." Print *speed* is not an auditable business event; per FBD-100358 the Activity Log records event types (Transaction, Annulment, Device Status, Defect, etc.), not print-duration measurements, so E2 does not correspond to the action. Also E1 states no concrete target time ("within the target print-speed time") — the numeric threshold from defect 301258 is unstated. | Drop the CloudFare S2/E2 step (or replace with the specific transaction event if issuance is in scope); state the concrete print-speed target value.

**C4100949** | Medium | salvageable-grounding / conflation | Non-functional performance test (defects 301276/301723/301598): E1 = "response times remain within acceptable limits with no progressive slow-down." S2/E2 again append the generic "corresponding event is recorded in CloudFare activity log," which does not correspond to a response-time/slow-down assertion — there is no audit event for "performance stayed acceptable." E1 also gives no concrete latency threshold. | Remove the CloudFare S2/E2 step; define the acceptable response-time limit(s) so the assertion is measurable.

**C4100945** | Low | needs-confirmation (grounding) | Deny/BIN list daily download and FEIG-concurrent update (defects 301106/302090), ETM "configured for Open Payments." EMV validation *is* grounded (screens 02.6.x exist), but "Deny/BIN list," "FEIG," and "Open Payments" configuration do not appear in the distilled ETM specs reviewed. Defect-driven so the capability is plausible, but unverified against a requirement. | Confirm Deny/BIN-list download + FEIG reader behaviour against the EMV/Open-Payments requirement (not in the FBD specs on hand); cite the source once found.

**C4100944** | Low | minor / needs-confirmation | Sequence-ID integrity across power loss (defect 301074) is coherent, but S2/E2 assert "the corresponding event is recorded in CloudFare activity log" without naming it. A restart plausibly maps to a Device Status event (FBD-100358), but sequence-ID resynchronisation itself is not a distinct audit event, so "the corresponding event" is ambiguous. | Name the actual expected Activity Log event (e.g. Device Status on restart) rather than "the corresponding event," or drop the step if none applies.

**C4100946** | Low | needs-confirmation (grounding) | GDPR passenger-display test (defect 300751). Precondition assumes "a customer-facing passenger display is connected" to the ETM; a separate passenger/customer display peripheral is not confirmed present on this ETM in the specs reviewed. Internally coherent; capability of the precondition needs verifying. | Confirm the ETM supports/attaches a customer-facing passenger display; if optional, state the config that enables it.
